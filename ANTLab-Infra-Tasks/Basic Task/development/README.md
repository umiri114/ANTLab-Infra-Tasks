# ANTLab Infra：本地大模型推理服务与性能测试

## 一、项目简介

本项目面向小型办公室及开发团队的本地大模型使用场景，基于 llama.cpp 部署量化大语言模型，并使用 FastAPI 构建 HTTP 接口，实现文本输入、文件内容处理、模型推理和请求日志记录等功能。

在服务部署完成后，通过单请求测试和不同并发级别的性能测试，分析服务的请求成功率、响应延迟和吞吐量，观察并发变化对整体服务性能的影响。

### 项目目标

- 部署可在本地 GPU 环境运行的大语言模型推理服务。
- 提供统一的 HTTP API，支持文本输入与文件内容处理。
- 记录请求执行信息，支持测试结果追踪。
- 建立可重复执行的单请求及并发性能测试。
- 根据实测数据分析性能表现，并提出合理的并发配置建议。

## 二、系统架构

系统主要由推理服务、API 后端和测试与日志模块组成。

```text
客户端 / 性能测试脚本
          |
          v
      FastAPI 后端
       端口 8000
          |
          v
  llama.cpp 推理服务
       端口 8080
          |
          v
Qwen2.5-3B-Instruct
       GGUF 模型
          |
          v
      返回推理结果
```

### 主要组件

| 组件 | 作用 |
|---|---|
| llama.cpp | 加载 GGUF 模型并提供本地推理服务 |
| llama-server | 提供兼容 OpenAI Chat Completions 格式的推理接口 |
| FastAPI | 处理客户端请求、文件输入和响应返回 |
| Python 测试脚本 | 执行单请求及并发性能测试 |
| JSON / JSONL 结果文件 | 保存性能统计和请求执行记录 |

## 四、功能实现

### 4.1 本地模型推理服务

使用 llama.cpp 加载 Qwen2.5-3B-Instruct Q4_K_M 模型，并通过 `llama-server` 对外提供推理接口。

服务支持接收对话请求并返回模型生成的内容，为上层 API 和性能测试提供推理能力。

### 4.2 FastAPI 请求接口

通过 FastAPI 构建后端接口，负责接收请求、组织输入内容、调用推理服务并返回结果。

当前实现包括：

- 接收用户文本输入。
- 支持指定本地文件路径并读取文件内容。
- 将输入内容组织为模型请求。
- 调用 llama.cpp 推理服务。
- 返回模型响应及相关请求信息。
- 记录请求执行时间、延迟和状态。

### 4.3 文件内容处理

系统支持读取指定的本地文本文件，并将文件内容与用户任务要求组合后发送给模型。

测试使用办公会议与项目进度资料作为输入，要求模型总结项目进展、识别存在的问题并提取下一步计划。

### 4.4 请求日志记录

API 将请求执行信息保存至：

`results/requests.jsonl`

日志用于追踪请求内容、输入文件、执行时间、延迟及请求状态，便于后续检查请求执行情况和分析测试结果。

### 4.5 性能测试

项目包含单请求与并发测试脚本：

- `tests/benchmark_single.py`
- `tests/benchmark_concurrent.py`

测试结果以 JSON 格式保存，便于复核数据并用于最终实验分析。

## 五、测试方法

本项目采用固定的办公文档总结任务作为测试负载，主要观察请求成功率、响应延迟和吞吐量。

### 5.1 单请求测试

- 请求次数：10 次。
- 记录平均延迟、最小延迟、最大延迟、P50 和 P95。
- 保存测试统计至 `tests/results/single.json`。

### 5.2 并发测试

- 并发级别：1、2、4。
- 每个并发级别执行 20 次正式请求。
- 正式测试前执行 1 次预热。
- 每个并发级别测试 1 轮。
- 保存测试统计至 `tests/results/concurrent.json`。

本次实验为各并发级别的单轮测试，因此结果反映当前测试条件下的观测表现，仍可通过增加重复轮数进一步验证稳定性。

## 七、实验分析

### 7.1 并发对吞吐量的影响

并发从 1 提升到 2 时，吞吐量由约 0.122 req/s 提升到约 0.218 req/s，增幅约为 78.3%。

这说明在本次工作负载下，适当提高并发能够提升整体请求处理效率。

当并发从 2 提升到 4 时，吞吐量仅从约 0.218 req/s 增加到约 0.224 req/s，增幅约为 3.0%。吞吐量增长明显放缓，表明继续提高并发没有带来相应幅度的处理能力提升。

### 7.2 并发对响应延迟的影响

并发从 1 提升到 2 时，平均延迟由约 8.19 秒增加到约 8.83 秒，变化相对有限。

当并发增加到 4 时，平均延迟上升至约 16.63 秒，P95 延迟达到约 19.92 秒。与并发 2 相比，高并发条件下的请求等待时间明显增加。

这表明并发增加虽然可能提高整体吞吐量，但也可能加剧请求之间的资源竞争，使单个请求的响应变慢。

### 7.3 并发配置建议

在本次实验条件下：

- **并发 1：** 单请求延迟相对较低，但总体吞吐量较低。
- **并发 2：** 吞吐量明显提高，平均延迟仍相对可控。
- **并发 4：** 吞吐量相较并发 2 提升有限，但平均延迟和 P95 延迟明显增加。

因此，**并发 2 可以作为当前工作负载下的候选配置**，在吞吐量与响应延迟之间取得较好的折中。

该建议仅适用于本次模型、硬件和输入条件。若要用于实际多人办公服务，还需要进一步测试不同输入长度、更多请求类型及持续运行情况下的性能表现。

## 九、当前限制与后续改进

当前版本已完成本地推理服务、API 接口、文件输入处理、请求日志和基本性能测试，但仍存在以下可改进之处：

1. **测试重复性：** 当前每个并发级别只进行一轮正式测试，后续可增加重复轮数并报告多轮统计结果。
2. **输入覆盖范围：** 当前以办公文档总结任务为主要负载，后续可加入不同文件长度、代码辅助等工作负载。
3. **业务正确性：** 当前主要统计 HTTP 请求状态和性能指标，后续可增加输出内容检查，以区分 HTTP 请求成功与任务内容正确。
4. **运行参数记录：** 应进一步核对 GPU 卸载层数、KV 缓存、Flash Attention 和生成参数，确保配置文件与实际启动参数一致。
5. **持续运行与恢复：** 可进一步测试服务异常、重启后的恢复情况，并记录故障与恢复时间。

## 十、结论

本项目完成了基于 llama.cpp 和 FastAPI 的本地大模型推理服务搭建，实现了文本请求、文件内容处理、API 调用和请求日志记录，并完成了单请求及不同并发级别的性能测试。

实测结果表明，在当前测试负载下，所有正式测试请求均获得 HTTP 200 响应。并发从 1 提升到 2 时，吞吐量显著提高；并发继续提升至 4 时，吞吐量增幅明显下降，而请求延迟大幅增加。

综合当前测试结果，并发 2 是值得进一步验证的候选配置。该项目建立了本地模型服务与性能测试的基本流程，并为后续的参数优化、负载扩展和稳定性测试提供了基础。
