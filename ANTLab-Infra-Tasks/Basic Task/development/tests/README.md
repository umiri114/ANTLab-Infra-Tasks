# Tests — 测试说明

## 1. 测试目标

本目录用于验证本地大模型推理服务的基本功能，并测量不同请求负载和并发级别下的服务性能。

测试主要关注：

- API 接口是否能够正常处理请求；
- 输入文件是否能够参与提示词构建；
- 请求是否成功完成；
- 请求延迟与吞吐量如何随并发级别变化；
- 测试结果能否保存为 JSON 文件，供后续分析和实验报告使用。

## 2. 目录结构

```text
tests/
├── README.md
├── test_api.sh
├── benchmark_single.py
├── benchmark_concurrent.py
└── results/
    ├── single.json
    └── concurrent.json
```

实际目录内容以仓库中的文件为准。

| 文件 | 用途 |
|---|---|
| `test_api.sh` | 检查 API 接口的基本可用性 |
| `benchmark_single.py` | 执行单请求场景的性能测试 |
| `benchmark_concurrent.py` | 测试不同并发级别下的请求性能 |
| `results/single.json` | 保存单请求测试的汇总结果 |
| `results/concurrent.json` | 保存并发测试的汇总结果 |

## 3. 测试环境与前置条件

执行测试前，需要确保：

1. llama.cpp 的 `llama-server` 已启动并监听配置的端口。
2. FastAPI 应用已启动，默认 API 地址为 `http://localhost:8000`。
3. Python 虚拟环境已安装项目所需依赖。
4. 测试脚本中配置的输入文件路径有效。
5. 测试输出目录存在，并且具有写入权限。

测试脚本中的 API 地址、输入文件路径和测试参数以实际代码为准。

## 4. 测试方法

### 4.1 API 功能测试

脚本：`test_api.sh`

该测试用于验证 API 的基本请求与响应行为。可在项目的 `Basic Task/development/` 目录下执行：

```bash
bash tests/test_api.sh
```

重点检查 HTTP 响应状态、返回内容，以及接口是否能够正常访问。

### 4.2 单请求性能测试

脚本：`benchmark_single.py`

执行方式：

```bash
python3 tests/benchmark_single.py
```

当前测试设置为 10 次请求，主要观察：

- 请求成功数与成功率；
- 平均延迟；
- 最小和最大延迟；
- P50 延迟；
- P95 延迟。

结果写入 `tests/results/single.json`。

### 4.3 并发性能测试

脚本：`benchmark_concurrent.py`

执行方式：

```bash
python3 tests/benchmark_concurrent.py
```

当前测试设置为：

| 参数 | 设置 |
|---|---|
| 并发级别 | 1、2、4 |
| 每个并发级别的正式请求数 | 20 |
| 预热请求数 | 1 |
| 每个并发级别的测试轮数 | 1 |

预热请求用于提前执行一次模型请求，不计入每个并发级别的 20 次正式请求。

结果写入 `tests/results/concurrent.json`。

## 5. 性能指标说明

| 指标 | 含义 |
|---|---|
| 成功数 | 测试中成功完成的请求数量 |
| 成功率 | 成功请求数占正式请求总数的比例 |
| 平均延迟 | 所有请求的平均处理时间 |
| 最小延迟 | 本轮测试观测到的最短请求延迟 |
| 最大延迟 | 本轮测试观测到的最长请求延迟 |
| P50 延迟 | 第 50 百分位延迟，可用于观察典型请求的耗时 |
| P95 延迟 | 第 95 百分位延迟，可用于观察较慢请求的表现 |
| 吞吐量 | 单位时间内完成的请求数，单位为 req/s |

指标的具体统计口径以测试脚本中的实现为准。

## 6. 当前实验结果

### 6.1 单请求测试

| 指标 | 结果 |
|---|---:|
| 正式请求数 | 10 |
| 成功数 | 10 |
| 成功率 | 100% |
| 平均延迟 | 0.763 秒 |
| 最小延迟 | 0.380 秒 |
| 最大延迟 | 1.644 秒 |
| P50 延迟 | 0.602 秒 |
| P95 延迟 | 1.579 秒 |

### 6.2 并发测试

| 并发级别 | 正式请求数 | 成功率 | 平均延迟 | 吞吐量 |
|---:|---:|---:|---:|---:|
| 1 | 20 | 100% | 8.187 秒 | 0.122 req/s |
| 2 | 20 | 100% | 8.833 秒 | 0.218 req/s |
| 4 | 20 | 100% | 16.625 秒 | 0.224 req/s |

### 6.3 结果分析

- 当前测试记录中的请求均成功完成。
- 并发级别从 1 增加到 2 时，吞吐量提高。
- 并发级别从 2 增加到 4 时，吞吐量提升有限，但平均延迟明显增加。
- 对当前并发测试负载而言，并发级别 2 值得作为性能与响应延迟之间的折中方案进一步评估。

需要注意，单请求与并发测试的输入负载可能不同，因此两组延迟不应直接视为同条件对比结果。以上结论也仅适用于当前测试环境和负载。

## 7. 结果保存与复现

测试结果以 JSON 格式保存，便于使用 Python 或其他分析工具进行读取和统计。

正式测试时建议保留：

- 使用的配置文件；
- 测试脚本版本；
- 输入负载与并发参数；
- 原始请求日志；
- 测试生成的 JSON 汇总结果。

逐请求运行记录保存在 `results/requests.jsonl`，模型与服务配置保存在 `configs/`，实验分析和结论整理在 `reports/`。

## 8. 当前测试范围与后续改进

目前测试覆盖 API 基本功能、单请求性能和多个并发级别下的性能表现。

后续可进一步增加异常输入、无效文件路径、超时、服务中断与恢复等测试，并通过多轮重复实验评估结果稳定性。

本目录中的测试结果用于描述已执行的实验，不代表尚未实施的故障恢复或长期稳定性测试已经通过。
