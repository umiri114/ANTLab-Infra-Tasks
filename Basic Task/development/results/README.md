# Results — 测试结果与运行记录

## 1. 目录用途

本目录用于保存本地大模型推理服务的请求记录及实验运行数据，为性能分析、故障排查和最终实验报告提供依据。

测试结果与 `configs/` 中的配置文件、`tests/` 中的测试脚本配合使用，以便追踪测试条件、请求执行情况和性能指标。

## 2. 目录结构

```text
results/
├── README.md
└── requests.jsonl
```

### 文件说明

| 文件 | 用途 |
|---|---|
| `README.md` | 说明测试结果目录的组织方式与数据用途 |
| `requests.jsonl` | 保存 API 请求的逐条运行记录，每行对应一条 JSON 记录 |

性能测试生成的汇总结果保存在 `tests/results/` 目录中，包括单请求测试和并发测试结果。

## 3. 请求日志格式

`requests.jsonl` 用于记录 FastAPI 接口处理请求时的相关信息。记录字段以实际代码输出为准，主要包括：

| 字段 | 含义 |
|---|---|
| `request_id` | 单次请求的标识，用于定位具体请求 |
| `prompt` | 请求使用的文本提示 |
| `file` | 请求关联的输入文件路径；没有关联文件时可能为空 |
| `start` | 请求开始时间 |
| `end` | 请求结束时间 |
| `latency` | 请求处理耗时，单位为秒 |
| `status` | 请求处理状态 |

日志采用 JSON Lines（JSONL）格式，每行是一个独立的 JSON 对象，便于追加写入、逐行解析和后续统计。

## 4. 性能测试结果

性能测试脚本位于 `tests/` 目录，汇总结果位于 `tests/results/`。

| 结果文件 | 测试内容 | 测试规模 |
|---|---|---|
| `tests/results/single.json` | 单请求场景下的响应性能 | 10 次请求 |
| `tests/results/concurrent.json` | 不同并发级别下的服务性能 | 并发级别为 1、2、4，每个级别 20 次正式请求 |

并发测试还包含 1 次预热请求。预热请求不计入每个并发级别的 20 次正式请求。

### 5.2 并发测试

| 并发级别 | 正式请求数 | 成功率 | 平均延迟 | 吞吐量 |
|---:|---:|---:|---:|---:|

以上数据来自当前保存的测试结果。单请求测试与并发测试的输入负载可能不同，因此两类结果不应直接用于严格的同条件性能对比。

### 5.3 初步分析

- 所有已记录的测试请求均成功完成，表明当前测试条件下 API 能够正常处理这些请求。
- 并发级别从 1 增加到 2 时，吞吐量有所提高。
- 并发级别从 2 增加到 4 时，吞吐量提升有限，同时平均延迟明显增加。
- 在当前测试负载下，并发级别 2 是值得进一步评估的折中选择，但该结论不代表所有工作负载下的最佳配置。

## 6. 与其他目录的关系

- `configs/`：记录模型、服务和测试配置，用于说明测试条件。
- `tests/`：保存单请求和并发测试脚本。
- `tests/results/`：保存性能测试生成的 JSON 汇总数据。
- `reports/`：整理测试方法、实验数据、分析和最终结论。

`results/requests.jsonl` 主要用于查看逐请求运行情况；`tests/results/*.json` 用于查看汇总性能指标。二者用途不同，不能相互替代。

## 7. 数据使用说明

正式实验分析应以实际生成的日志和 JSON 结果为依据。若重新运行测试并覆盖汇总文件，应确认保存的配置、测试脚本和结果属于同一次实验。

后续可在此基础上增加独立的运行编号、配置版本标识和故障恢复记录，以进一步提高实验的可追溯性。
